# Ollama Harness — Project Memory

This is the running notebook home page. Open this `docs/` folder as an Obsidian vault to browse it with backlinks/graph view. This file is the index — decisions and open questions live here, background detail lives in the linked notes.

## What this is

A modular starter for building a custom Ollama-backed agent/harness — deliberately not the stock Open WebUI. Two tracks: a UI ([[Architecture/Frontend]]) and a harness/control-plane ([[Architecture/Backend]]), meant to converge into a desktop app rather than a browser webui.

## Current state

- `ui/` — working React + Vite + TS chat scaffold, talks directly to a local Ollama instance. See `ui/README.md` for how it's structured. This is a starting point, not the final shell (see delivery decision below).
- Everything else described here is still in the planning stage — no harness or desktop shell code exists yet.

- **2026-08-14 — Theme pack system + titlebar theme picker.** User request: "style this chat a bit better... with some theme pickers... an options menu sort of like we have for the show tasks toggle... make it customizable with packs (so a user could load one if someone else creates one)" — with "Psyduck Yellow" as the first custom pack. Built as a **pack system, not a hardcoded theme list**, because the whole UI already consumes colors exclusively from the ~12 CSS custom properties in `index.css` (no component hardcodes a color) — so a complete reskin is just a new palette, and "someone else's pack" is just a JSON file of `{ id, name, author?, description?, scheme?, vars }`. `lib/themes.ts`: registry + `sanitizeThemePack` + persistence + `applyThemePack`. **Security posture (packs are untrusted input, and applying one injects CSS text):** ids and var names regex-checked, values must be plain color literals (hex/rgb/rgba/hsl/hsla/transparent) — invalid entries are *skipped*, never injected, with a readable error when nothing usable remains; unknown `vars` keys are skipped rather than failed so a pack can introduce a variable a future component uses (forward-compat). **Built-in packs defined in TS** (so the picker can render swatches/blurbs and apply works identically for built-in and imported): `auto` (removes `data-theme`, prefers-color-scheme decides — today's behavior), `light`/`dark` (mirror the index.css base/system-dark palettes; noted in-file to keep in sync if index.css is restyled), `psyduck-yellow` (first accent-variant pack, "Confused about its own colors. Do not ask."). **Applying:** `data-theme` on `<html>` + a persistent `<style>` element injecting the pack's vars scoped to `:root[data-theme="…"]` (beats both the base palette and the system-dark override, which was scoped to `:root:not([data-theme])` in index.css so it only governs `auto`); per-pack `color-scheme` so scrollbars match. **`ThemePicker.tsx`:** 🎨 button in the titlebar next to the ☰/⚙ toggles (with `app-region: no-drag` — the popover sits inside the drag-region titlebar), popover with swatch rows (auto gets a split light/dark swatch since it's not a palette), imported-packs section with per-pack delete (deleting the active pack falls back to auto), paste-JSON import, and file import through a new `read_theme_pack` Tauri command (plain `fs::read_to_string` in `commands.rs` + 2 unit tests — no parsing in Rust, validation lives on the JS side before anything touches the DOM). **Persistence:** `ollama-ui:active-theme` + `ollama-ui:themes` in localStorage, same pattern as base-url/sidebar-collapsed; a saved id that no longer resolves falls back to auto rather than stranding the app unstyled. - **2026-08-15 — Patch/diff-style `edit_file` tool built, closing a real bug (not just a predicted risk).** `write_file`'s full-overwrite semantics had already silently dropped a concurrent edit to `App.css` during a dogfood turn — recovered only because git existed by then. Deliberately shaped like Claude Code's own `Edit` tool (`old_string`/`new_string` find-replace, unique-match-or-error, optional `replace_all`) rather than a unified-diff format: line-numbered diff hunks drift and are much harder for a small dispatch model (`qwen3.5:9b`) to produce correctly than an exact-text find-replace. Reads the file's current on-disk content at call time, so a stale read earlier in the conversation fails the match loudly instead of silently clobbering whatever changed underneath it — the actual fix for the collision class, not just a smaller blast radius. `write_file`'s tool description now nudges the model toward `edit_file` for existing files. 4 new Rust unit tests pass; `cargo check`/`tsc --noEmit` clean.

- **2026-08-15 — Real bug found on `edit_file`'s first live call, with a wider blast radius than just that one tool.** The model's call failed: `"command edit_file missing required key oldString"`. Root cause: Tauri v2's `#[tauri::command]` macro defaults to matching JS-supplied argument keys as **camelCase** against Rust parameter names — so the Rust param `old_string` (matching the snake_case JSON tool schema sent to Ollama, and the model's own tool-call arguments, forwarded to `invoke()` unmodified) only ever matched a literal `oldString` key, which nothing sends. Checking the rest of the tool set turned up the same latent bug already sitting in `search_files` (`file_glob`/`case_sensitive`/`max_results`) and `execute_command` (`working_dir`) — both still marked "not yet exercised live" in Kanban, which is very possibly *why* it hadn't surfaced yet rather than evidence those tools worked. Fixed with `#[tauri::command(rename_all = "snake_case")]` on all affected commands (`edit_file`, `search_files`, `execute_command`, plus the new `mcp_call_tool`) — keeps Rust's snake_case naming and the existing JSON schemas as-is, just opts out of Tauri's camelCase default. Worth remembering for any *future* Tauri command with a multi-word parameter: add `rename_all = "snake_case"` up front, don't wait to rediscover this.

- **2026-08-15 — MCP connector support built: real protocol work, not a placeholder.** Hand-rolled a JSON-RPC 2.0 stdio client (`src-tauri/src/mcp.rs`) rather than pulling in an MCP SDK crate — consistent with this project's existing pattern of hand-rolling protocol clients (`harness/loopx_client.py`, `harness/ollama.py`, `kanban.rs` are all the same choice), and the stdio transport itself is simple enough to justify it (one JSON-RPC message per line, no extra framing). Connection lifecycle (spawned child process, `initialize` handshake, `tools/list`, per-request response correlation via a background reader thread + channel map, capped stderr capture surfaced on connect failure) lives entirely in Rust, keyed by a server id in Tauri-managed state; the frontend (`lib/mcp.ts`, `hooks/useMcpServers.ts`) only owns server *config* (name/command/args), persisted in localStorage like every other app-level setting. MCP tools are qualified as `mcp__<serverId>__<toolName>` (matches Claude's own MCP naming convention) so `skills.ts::executeSkill` can route a call to the right server without a second lookup table, and are merged into what `useChat` sends to Ollama alongside the built-in skills.
