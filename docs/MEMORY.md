# Ollama Harness — Project Memory

This is the running notebook home page. Open this `docs/` folder as an Obsidian vault to browse it with backlinks/graph view. This file is the index — decisions and open questions live here, background detail lives in the linked notes.

## What this is

A modular starter for building a custom Ollama-backed agent/harness — deliberately not the stock Open WebUI. Two tracks: a UI ([[Architecture/Frontend]]) and a harness/control-plane ([[Architecture/Backend]]), meant to converge into a desktop app rather than a browser webui.

## Current state

- `ui/` — working React + Vite + TS chat scaffold, talks directly to a local Ollama instance. See `ui/README.md` for how it's structured. This is a starting point, not the final shell (see delivery decision below).
- Everything else described here is still in the planning stage — no harness or desktop shell code exists yet.

## Decisions log

- **2026-08-14 — UI scaffold stack.** React + Vite + TS, direct calls to Ollama's local HTTP API (`http://localhost:11434`), no backend yet. Chosen for fast component iteration; easy to swap the transport layer later without touching the rest of the app.
- **2026-08-14 — Direction opened up beyond a plain chat UI.** Backend should be a control-plane (not just request/response chat), UI should support more than one presentation paradigm, and delivery should be a desktop widget/app, not a webui.
- **2026-08-14 — Reference tool corrected: [nanoclaw](https://nanoclaw.dev/), not "openclaw".** Node.js host orchestrating per-session Docker containers (Bun + Claude Agent SDK inside), skills as an on-demand-installed registry, credentials behind a vault. Messaging-platform-first, not desktop-automation-first. The transferable idea is *skills-as-installable-modules + per-skill isolation* — not the Claude Agent SDK / messaging-channel parts, since this project runs local Ollama models and drives the desktop instead. Detail: [[Architecture/Backend]].
- **2026-08-14 — Control plane: adopt [loopx](https://github.com/huangruiteng/loopx) as-is.** It's a governance layer (durable objectives, todos, user gates, evidence logs, quota) that sits *above* a harness — it does not replace Ollama calls, streaming, or tool dispatch. Chose adopt-as-is over reimplementing for speed, given the heavy-focus timeline. Detail: [[Architecture/Backend]].
- **2026-08-14 — Toy long-running task candidates: app/game building, or data science/engineering work.** Motivated by wanting a Karpathy-style (minimal, legible, no-magic) harness. Exact pick is still an open question (see below).
- **2026-08-14 — Image/comic-strip generation deferred.** Ollama models — including the vision-capable `qwen3.8-27b` (`hf.co/unsloth/Qwen3.8-27B-GGUF`) currently being tested — accept image input but cannot generate images. A SillyTavern-style "illustrate this scene" feature would need a second local backend (e.g. ComfyUI/SDXL) called alongside Ollama. Deferred to v1+, but the harness's tool-dispatch layer should stay open to a second backend rather than being hardwired to Ollama only.
- **2026-08-14 — Delivery shell: Tauri, glass-style aesthetic.** Corner-pop / own-window / can-drive-the-OS, not a browser tab — a plain webui can't do window-manager-level behavior, and retrofitting that later is worse than deciding it now. Rust shell + the existing React content pane from `ui/`. Ties into an existing interest in learning Rust on a real component rather than the whole app. Detail: [[Architecture/Frontend]].
- **2026-08-14 — Glass desktop app floated as a possible dogfood "toy task"** (harness helps build its own UI) — sequenced as a phase 2/3 stretch once the harness is proven headless, not a day-1 task (agent editing its own live runtime is a bad first date).
- **2026-08-14 — Timeline locked in.** Heavy-focus time budget (phases measured in days, not weeks); harness and shell built **in parallel**, not sequentially; loopx adopted as-is; image-gen deferred. Full phase breakdown: [[Timeline]].
- **2026-08-14 — Toy task decided: a throwaway practice desktop utility, built in Tauri/Rust** — deliberately the *same tech family* as the real shell but disposable, so the harness/loopx loop gets proven before it's trusted near the real app. Explicitly **not** the real desktop app itself (that stays a Phase 3 stretch, see [[Timeline]]) and **not** app/game-vs-data-sci in the abstract — a concrete, scoped-to-finish choice.
- **2026-08-14 — Specific toy utility: a read-only Kanban-board-reader popup** that parses and renders `docs/Kanban.md`. Chosen because it's dual-purpose — real Tauri/Rust practice, plus a low-stakes first taste of the companion/game-menu presentation styles being weighed for the real UI (see [[Architecture/Frontend]]), applied to something disposable before either style gets committed to the actual chat app. **Scoped read-only on purpose**: a parsing/serialization bug that corrupts the real DevOps board would undercut the whole point of it being a safe throwaway task. Write-back (checking off cards from the popup) is a plausible fast-follow, not a Phase 1 requirement.

- **2026-08-14 — Skill/tool-dispatch architecture deferred to Phase 2, not designed up front.** The Phase 1 toy task only needs a deterministic file-read (parsing `docs/Kanban.md`) plus a plain Ollama call for companion-style commentary — no real dispatch decision involved, so there's nothing concrete to design the architecture against yet. When Phase 2's first real OS-level skill exists, the lean is **model-directed dispatch** (Ollama's native tool-calling/`tools` API — the LLM decides when to invoke a skill) over harness-directed (code decides deterministically). See [[Architecture/Backend]] for the model-capability implication this creates.
- **2026-08-14 — [`unsloth/Qwen3.8-27B-GGUF`](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF) confirmed as the main/primary model**, not just "currently under test." 27B dense hybrid architecture, 262K context (extendable to 1M), thinking mode on by default, upstream-designed for tool-calling and long-horizon agentic tasks. **Intended harness shape: the harness exposes tool/skill definitions that *smaller* local models (`gemma4:26b`, `qwen3.5:9b`) drive dispatch decisions with — the 27B is not meant to be swapped out for this, it stays the main model for heavier generation/reasoning.** Corrects an earlier note that read as "the 27B lacks tool-calling so swap it out" — the real story is more precise: the local quantized build reports no `tools` capability in Ollama despite the upstream model supporting function calling (likely a template/packaging gap, low-priority to chase). See [[Architecture/Backend]].

- **2026-08-14 — loopx wiring built and proven, with a real platform/complexity finding.** loopx requires a genuine POSIX environment (its own installer and CLI depend on Python's `fcntl`, Unix-only) — native Windows Python can't run it at all, Git Bash doesn't change that since it's still native Windows Python underneath. Installed WSL2 Ubuntu (WSL2 itself was already enabled via Docker Desktop) with a non-root default user, installed loopx there (v0.4.3, healthy per `loopx doctor`), and bootstrapped a real goal for the toy project at `toys/kanban-reader/` (`goal_id=kanban-reader-goal`, `agent_id=ollama-harness-01`). **Separately, worth flagging: loopx in practice is far heavier than its README's "lightweight state kernel" framing suggested** — `quota should-run` alone returns 300+ lines of JSON covering Codex-App-specific automation contracts, heartbeat prompts, promotion-readiness gates, canary tracking, and multi-agent coordination primitives that don't apply to a solo Ollama-harness use case. It's still usable: a thin harness only needs to read ~5 fields (`should_run`, `selected_todo.todo_id/text/priority`) out of that payload, and the rest can be ignored. `harness/loopx_client.py` (native Windows Python, subprocess-shells into `wsl -d Ubuntu -- loopx ...`) proved a full real cycle: `should_run` → genuine Ollama call (`harness/ollama.py`) → `todo complete` with real evidence → `refresh-state` → `quota spend-slot`, all succeeding. The real P0/P1/P2 project todos (scaffold/parse/render) were deliberately left open rather than marked done from a wiring test — a separate throwaway smoke-test todo was used to prove the mechanics honestly.

- **2026-08-14 — Tauri scaffold built into `toys/kanban-reader/`** via `npm create tauri-app` (vanilla-ts template, npm package manager, identifier `dev.meansquares.kanbanreader`). Rust toolchain (rustup, stable-msvc) and Tauri's MSVC C++ build tools were both installed/confirmed on this machine as part of this. **Incident along the way:** the scaffold's `--force` flag wiped the `.loopx/`/`.codex/goals/` state that had just been proven working, since it deletes-and-recreates the target directory rather than merging. Recovered cleanly (`loopx retire-global-goal` → re-bootstrap → re-add the same 3 todos, which came back with identical deterministic IDs) — no real project work was lost. Full detail and the general lesson: [[Architecture/Backend]].

- **2026-08-14 — Phase 3 started: thinking breakout, and a real bug caught by proper diagnosis.** Added streamed thinking tokens (`onThinking` in `lib/ollama.ts`, mirrors how `content` already streamed) and a collapsible thought-process section in `MessageBubble.tsx` (collapsed by default, label flips "Thinking…" → "Thought process" once real content starts). User reported a message stuck showing "Thinking…" forever with no further progress. **Diagnosed properly rather than guessed:** checked live process state (`Get-Process` — found the actual `llama-server` runner by memory footprint since it isn't named obviously) and Ollama's `server.log`. The request had genuinely finished — 200 OK after 1m31s — but hit `n_ctx_slot=4096` and got `truncated=1` while still inside the thinking phase, so it never emitted real `content`. **The actual bug was in our UI, not Ollama or the model:** the "still thinking" state was derived only from the message's own fields (thinking present, content empty), with no reference to whether the stream had actually ended — so a thinking-only truncated response stayed stuck forever with no way to distinguish "still working" from "done, but produced nothing." Fixed: only the actively-streaming message now shows "Thinking…"; a stream that ends with no content shows an explicit "no response — likely ran out of context" message. Also bumped `DEFAULT_PARAMS.numCtx` 4096→8192 for new conversations (existing ones keep their saved value) — flagged the RAM/VRAM tradeoff rather than jumping straight to the 32768 max the Settings slider already allows.

Moved to Backlog as an open investigation (next lead: WebView2's own independent compositor background) rather than declared done or silently dropped. - **2026-08-14 — Live tool-dispatch shipped: the actual thing the user wanted.** Prompted by direct feedback: "It should be able to write files (with approval)... maybe have the ability to open a folder... kinda my whole thing with how we have it running" (i.e., work like Claude Code — read/write/browse, gated by approval). - **2026-08-14 — Theme pack system + titlebar theme picker.** User request: "style this chat a bit better... with some theme pickers... an options menu sort of like we have for the show tasks toggle... make it customizable with packs (so a user could load one if someone else creates one)" — with "Psyduck Yellow" as the first custom pack. Built as a **pack system, not a hardcoded theme list**, because the whole UI already consumes colors exclusively from the ~12 CSS custom properties in `index.css` (no component hardcodes a color) — so a complete reskin is just a new palette, and "someone else's pack" is just a JSON file of `{ id, name, author?, description?, scheme?, vars }`. `lib/themes.ts`: registry + `sanitizeThemePack` + persistence + `applyThemePack`. **Security posture (packs are untrusted input, and applying one injects CSS text):** ids and var names regex-checked, values must be plain color literals (hex/rgb/rgba/hsl/hsla/transparent) — invalid entries are *skipped*, never injected, with a readable error when nothing usable remains; unknown `vars` keys are skipped rather than failed so a pack can introduce a variable a future component uses (forward-compat). **Built-in packs defined in TS** (so the picker can render swatches/blurbs and apply works identically for built-in and imported): `auto` (removes `data-theme`, prefers-color-scheme decides — today's behavior), `light`/`dark` (mirror the index.css base/system-dark palettes; noted in-file to keep in sync if index.css is restyled), `psyduck-yellow` (first accent-variant pack, "Confused about its own colors. Do not ask."). **Applying:** `data-theme` on `<html>` + a persistent `<style>` element injecting the pack's vars scoped to `:root[data-theme="…"]` (beats both the base palette and the system-dark override, which was scoped to `:root:not([data-theme])` in index.css so it only governs `auto`); per-pack `color-scheme` so scrollbars match. **`ThemePicker.tsx`:** 🎨 button in the titlebar next to the ☰/⚙ toggles (with `app-region: no-drag` — the popover sits inside the drag-region titlebar), popover with swatch rows (auto gets a split light/dark swatch since it's not a palette), imported-packs section with per-pack delete (deleting the active pack falls back to auto), paste-JSON import, and file import through a new `read_theme_pack` Tauri command (plain `fs::read_to_string` in `commands.rs` + 2 unit tests — no parsing in Rust, validation lives on the JS side before anything touches the DOM). **Persistence:** `ollama-ui:active-theme` + `ollama-ui:themes` in localStorage, same pattern as base-url/sidebar-collapsed; a saved id that no longer resolves falls back to auto rather than stranding the app unstyled. Theme is **app-level**, deliberately not in the per-conversation SettingsPanel (which stays model/prompt/params). **Deliberately built on top of the glass, not around it:** all pack colors stay translucent `rgba()` so any pack — including future community ones — picks up the real Mica/Acrylic backdrop the moment that Backlog investigation resolves (user confirmed the glassy look "isn't really working yet but that's the goal down the line"). Pure frontend + one small Rust read command. Added to [[Kanban]] "To Test" — `tsc`/`cargo` run and live verification pending.
